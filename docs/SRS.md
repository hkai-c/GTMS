## 1. 引言

### 1.1 编写目的

本文档旨在详细定义**磨床试磨管理系统（GTMS）V1.0**的全部功能需求和非功能需求，作为开发、测试、验收的依据。

### 1.2 范围

本系统覆盖磨床制造企业从**销售接单 → 收件 → 试磨 → 检测 → 工件去向**的全流程数字化管理，支持 Windows 桌面客户端、微信小程序两端访问。

### 1.3 术语定义

| 术语 | 说明 |
|------|------|
| 试磨任务 | 客户委托进行磨床试磨加工的一个完整工作单元 |
| 试磨件 / 工件 | 客户寄送过来进行试磨的实体零件 |
| 任务编号 | 系统自动生成的唯一编号，格式 `TM202600001` |
| 收件 | 技术员收到客户寄来的工件并登记 |
| 试磨责任人 | 实际执行试磨操作的技术员 |
| 检测报告 | 试磨完成后对工件精度和粗糙度的检测结果文件 |
| 工件去向 | 工件最终的去向（寄回客户 / 留存 / 报废等） |
| RBAC | 基于角色的访问控制（Role-Based Access Control），用户通过角色获得权限 |

- 《GTMS 数据库设计说明书》

## 2. 总体描述

### 2.1 产品视角

GTMS 是一个典型的三层架构企业管理系统：

```
┌──────────────┐   ┌──────────────┐
│ Windows 桌面端│   │  微信小程序   │
│  (PySide6)   │   │  (UniApp)   │
└──────┬───────┘   └──────┬───────┘
       │                  │
       └────────┬─────────┘
                │ HTTP REST API
       ┌────────┴─────────┐
       │  FastAPI 后端服务  │
       │  (业务逻辑层)      │
       └────────┬─────────┘
                │
       ┌────────┴─────────┐
       │  SQLite / MySQL   │
       └──────────────────┘
```

### 2.2 用户特征

| 角色（RBAC） | 技术水平 | 使用频率 | 主要操作端 |
|------|------|------|------|
| 销售 | 基础电脑操作 | 每天 5-10 次 | Windows 桌面端 |
| 技术员 | 基础电脑操作 | 每天 10-20 次 | Windows 桌面端 + 微信小程序 |
| 管理员 | 熟悉电脑操作 | 每周 2-3 次 | Windows 桌面端 |
| 领导 | 基础电脑操作 | 每天 1-2 次 | 微信小程序为主 |

> 角色可通过后台由管理员分配，支持一个用户拥有多个角色。

### 2.3 假设与约束

- 假设企业有局域网环境，桌面端通过内网访问后端服务
- 微信小程序需要 HTTPS 域名（生产环境）
- 单企业使用，不涉及多租户
- 工件去向只记录最终去向，不涉及物流跟踪

## 4. 功能需求详述

### 4.1 FR-AUTH — 认证模块

#### FR-AUTH-01 用户登录

| 字段 | 值 |
|------|------|
| **优先级** | 高 |
| **输入** | 用户名（必填，字符串）、密码（必填，字符串） |
| **处理** | 1. 校验用户名是否存在 2. 校验密码是否正确（bcrypt） 3. 校验用户是否启用 4. 生成 JWT Token（含 user_id、roles列表、permissions列表，有效期 8 小时） 5. 返回 Token + 用户信息 |
| **输出** | `{ token, user: { id, username, real_name, roles: [...], permissions: [...] } }` |
| **异常** | 用户名不存在 → "用户名或密码错误"；账号已禁用 → "账号已被禁用，请联系管理员" |

#### FR-AUTH-02 修改密码

| 字段 | 值 |
|------|------|
| **优先级** | 中 |
| **输入** | 旧密码、新密码（至少6位）、确认新密码 |
| **校验规则** | 新密码长度 ≥ 6 位；新密码 ≠ 旧密码；新密码 = 确认新密码 |
| **输出** | 成功提示 |

#### FR-AUTH-03 角色管理

| 属性 | 说明 |
|------|------|
| **权限** | 仅管理员 |
| **功能** | 创建角色、编辑角色、删除角色、为角色分配权限 |
| **约束** | 系统角色（is_system=true）不可删除 |

#### FR-AUTH-04 权限管理

| 属性 | 说明 |
|------|------|
| **权限** | 仅管理员 |
| **功能** | 查看权限列表（按模块分组），权限不可增删改（代码定义） |
| **说明** | 权限由代码定义，管理员只能查看和分配，不能修改权限定义 |

### 4.3.1 BR-TASK — 任务责任人与权限规则

#### BR-TASK-01 责任人独立原则

系统中各业务阶段的责任人互相独立，不要求为同一人员。

同一个试磨任务可由不同技术员分别完成不同业务环节。

例如：

* 技术员 A：收件登记
* 技术员 B：开始试磨、完成试磨
* 技术员 C：上传检测报告
* 技术员 D：填写工件去向

系统分别记录每个阶段的实际操作人。

---

#### BR-TASK-02 权限控制原则

系统采用**阶段权限（Stage Permission）**控制，而不是采用固定责任人控制。

具有对应模块权限的用户即可执行对应业务操作，同时系统自动记录当前操作人为该阶段责任人。

例如：

| 业务阶段   | 权限要求              | 操作人记录                       |
| ------ | ----------------- | --------------------------- |
| 收件登记   | receipt:create    | Receipt.created_by          |
| 开始试磨   | grinding:start    | GrindingRecord.operator_id  |
| 完成试磨   | grinding:finish   | GrindingRecord.operator_id  |
| 上传检测报告 | inspection:create | InspectionRecord.created_by |
| 填写工件去向 | dispatch:create   | Dispatch.created_by         |

---

#### BR-TASK-03 试磨责任人

"开始试磨"时指定的"试磨责任人"仅表示本次试磨工作的负责人。

后续允许其他具有权限的技术员代为完成检测、上传报告或填写工件去向。

系统始终保留各阶段实际操作人的记录。

---

#### BR-TASK-04 审计原则

所有业务操作均写入 SystemLog。

日志至少记录以下内容：

* 操作时间
* 操作用户
* 操作类型
* 所属任务
* 操作结果
* 状态变更

保证全过程可追溯。

---

#### BR-TASK-05 与权限系统关系

本规则不影响 RBAC 权限模型。

用户是否能够执行某一步操作，仅由其拥有的权限决定，而不由上一阶段操作人员决定。

任务状态（process_status）负责控制业务流程是否允许进入下一阶段；权限系统负责控制当前登录用户是否具有执行该操作的权限。

二者共同组成完整的业务控制机制。

### 4.5 FR-GRINDING — 试磨管理模块

#### FR-GRINDING-01 开始试磨

| 字段 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| 试磨责任人 | 下拉选择 | ✅ | 从技术员角色用户中选择 |
| 工件领出时间 | 日期时间 | ✅ | 默认当前时间 |

**业务规则：**
- 仅 process_status=received 状态的任务可操作
- 提交后 process_status 变为 grinding

========================
责任人与操作人规则
========================

本项目采用：

"当前登录技术员" 与 "试磨责任人" 分离设计。

规则如下：

1. 收件

任意 Technician 可执行。

收件人员不固定。

2. 开始试磨

当前登录 Technician 接受管理员分配的试磨任务，或主动领取未分配的试磨任务。

系统自动将当前登录用户设为试磨负责人：

GrindingRecord.operator_id = current_user.id

试磨负责人一经确定，在试磨结束前不得修改。

3. 完成试磨

仅允许：

- 试磨负责人；
- 管理员。

其他技术员无权完成试磨。

4. 检测

任意 Technician 可执行。

系统记录实际操作人。

5. 工件去向

任意 Technician 可执行。

系统记录实际操作人。

6. 通知规则

试磨任务任意阶段发生超时，

系统自动通知：

① 当前试磨负责人；

② 创建该任务的销售（created_by）；

③ 管理员。

不得通知收件人员。

不得通知去向人员。

7. 数据库约束

本规则不得修改 Sprint 1 已完成 ORM 设计。

#### FR-GRINDING-02 完成试磨

| 字段 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| 完成时间 | 日期时间 | ✅ | 默认当前时间 |
| 试磨机型 | 文本 | | 如"MGK-300" |
| 砂轮型号 | 文本 | | 如"WA80K" |
| 加工参数 | 多行文本 | | 转速、进给量等 |
| 试磨图片 | 图片和视频上传 | | 最多 10 张 |
| 试磨结果 | 单选 | ✅ | 成功 / 失败 |

- 如果失败，任务结束，不需要后续检测和去向

|------|------|

| SQL 注入防护 | 使用 ORM 参数化查询 |
| 操作审计 | 所有修改操作记录日志 |

### 5.3 可用性需求

### 5.5 可维护性需求

## 6. 数据字典

### 6.1 流程状态枚举（process_status）

| 状态值 | 中文名称 | 含义 | 可流转至 |
|------|------|------|------|
| `created` | 已创建 | 销售创建试磨任务 | `received` |
| `received` | 已收件 | 公司收到客户工件 | `grinding` |
| `grinding` | 试磨中 | 技术人员开始试磨 | `dispatched` |
| `dispatched` | 已寄回 | 工件已寄回客户 | `closed` |
| `closed` | 已关闭 | 任务结束归档 | (终态) |

**流转规则：** 严格单向，禁止跳级，禁止逆向，closed 为终态。

### 6.2 结果状态枚举（result_status）

| 状态值 | 中文名称 | 含义 | 可流转至 |
|------|------|------|------|
| `pending` | 待试磨 | 尚未完成试磨 | `passed`, `failed` |
| `passed` | 试磨成功 | 已上传检测报告且合格 | (终态) |
| `failed` | 试磨失败 | 无法满足加工要求 | (终态) |

**流转规则：** 不可逆（passed/failed 不可互转），passed 和 failed 均为终态。

### 6.3 工件去向枚举（destination）

| 状态值 | 中文名称 | 含义 |
|------|------|------|
| `returned_customer` | 寄回客户 | 工件寄回客户 |
| `retained_company` | 公司留样 | 公司保留样件 |
| `scrapped` | 报废 | 工件报废 |
| `returned_sales` | 返回销售 | 返回销售人员 |
| `other` | 其他 | 其它情况 |

### 6.4 失败原因（failure_reason）

仅当 `result_status = failed` 时填写，常见原因包括：

- 材料问题
- 精度达不到
- 设备能力不足
- 客户取消
- 其它原因

### 6.5 文件类型枚举

| 值 | 含义 | 扩展名 |
|------|------|------|
| `image` | 图片 | .jpg, .jpeg, .png |
| `document` | 文档 | .pdf, .docx, .xlsx |
| `cad` | CAD文件 | .dwg, .dxf |
| `video` | 视频 | .mp4 |

### 6.6 通知类型枚举

| 值 | 含义 |
|------|------|
| `receipt_delay` | 收件超时未试磨 |
| `grinding_delay` | 试磨超时未完成 |
| `report_missing` | 检测报告未上传 |

### 6.7 操作类型枚举

| 值 | 含义 |
|------|------|
| `create` | 创建 |
| `update` | 修改 |
| `delete` | 删除 |
| `status_change` | 状态变更 |

## 7. 状态机定义

### 7.1 流程状态流转图（process_status）

```
                     ┌─────────────────┐
                     │    created       │ ← 销售创建任务
                     │    (已创建)       │
                     └────────┬────────┘
                              │ 技术员收件登记 [FR-RECEIPT-01]
                              ▼
                     ┌─────────────────┐
                     │    received      │
                     │    (已收件)       │
                     └────────┬────────┘
                              │ 技术员开始试磨 [FR-GRINDING-01]
                              ▼
                     ┌─────────────────┐
                     │    grinding      │
                     │    (试磨中)       │
                     └────────┬────────┘
                              │ 技术员填写工件去向 [FR-DISPATCH-01]
                              ▼
                     ┌─────────────────┐
                     │   dispatched     │
                     │   (已寄回)        │
                     └────────┬────────┘
                              │ 管理员归档
                              ▼
                     ┌─────────────────┐
                     │    closed        │  ← 终态
                     │   (已关闭)        │
                     └─────────────────┘
```

### 7.2 结果状态流转图（result_status）

```
                     ┌─────────────────┐
                     │    pending       │ ← 任务创建时默认
                     │    (待试磨)       │
                     └────────┬────────┘
                       ┌──────┴──────┐
                       │             │
                [检测合格]       [检测不合格]
                       │             │
                       ▼             ▼
              ┌───────────┐  ┌───────────┐
              │  passed   │  │  failed   │
              │ (试磨成功) │  │ (试磨失败) │
              └───────────┘  └───────────┘
                 终态             终态
```

### 7.3 流程状态流转矩阵

| 当前 ↓ / 目标 → | created | received | grinding | dispatched | closed |
|:------|:--:|:--:|:--:|:--:|:--:|
| **created** | — | ✅ | ❌ | ❌ | ❌ |
| **received** | ❌ | — | ✅ | ❌ | ❌ |
| **grinding** | ❌ | ❌ | — | ✅ | ❌ |
| **dispatched** | ❌ | ❌ | ❌ | — | ✅ |
| **closed** | ❌ | ❌ | ❌ | ❌ | — |

### 7.4 结果状态流转矩阵

| 当前 ↓ / 目标 → | pending | passed | failed |
|:------|:--:|:--:|:--:|
| **pending** | — | ✅ | ✅ |
| **passed** | ❌ | — | ❌ |
| **failed** | ❌ | ❌ | — |

### 7.5 状态流转权限

| 流转 | 操作角色 |
|------|------|
| created → received | 技术员 |
| received → grinding | 技术员 |
| grinding → dispatched | 技术员 |
| dispatched → closed | 管理员 |
| pending → passed | 技术员 |
| pending → failed | 技术员 |

## 8. 业务规则汇总

| 编号 | 规则 | 模块 |
|------|------|------|
| BR-01 | 任务编号格式：TM + 年份(4位) + 5位序号，每年重置 | 任务 |
| BR-02 | 任务编号不可修改 | 任务 |
| BR-03 | process_status=created 状态的任务可编辑基本信息 | 任务 |
| BR-04 | process_status 流转不可逆向（进入 received 后不可回退到 created） | 任务 |
| BR-05 | 有客户关联的任务不可删除客户 | 客户 |
| BR-06 | 收件至少上传 1 张图片 | 收件 |

| BR-08 | result_status 不可逆（passed/failed 不可互转） | 检测 |

| BR-10 | 单次上传文件不超过 50MB (文档) / 10MB (图片) / 200MB (视频) | 附件 |
| BR-11 | 操作日志不可删除 | 日志 |
| BR-12 | 消息提醒不重复生成（已有未读提醒则跳过） | 通知 |
| BR-13 | 用户只能看到自己角色的消息通知 | 通知 |
| BR-14 | 禁用的用户无法登录 | 认证 |
| BR-15 | 仅销售可编辑自己创建的任务 | 任务 |

## 9. 验收标准

### 9.1 功能验收

| 编号 | 验收项 | 通过标准 |
|------|------|------|

| AC-10 | 统计报表 | 本月/年度数量、成功率、客户排行、机型排行正确 |
